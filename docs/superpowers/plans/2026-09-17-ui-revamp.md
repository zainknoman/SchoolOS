# UI Revamp — Parent App Visual Refresh + Profile Headers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the Flutter parent-app a premium, mobile-native visual language (currently default
Material — bare `CircleAvatar`, no iconography, undifferentiated card styling), and add a proper
profile-header to the staff-console's `StudentProfileView`/`StaffProfileView` (currently a bare `<h1>`
above a definition-list). Purely visual/presentational work — no new backend endpoints, no changed
business logic, no renamed/removed `Key`/`data-testid` hooks.

**Architecture:** No new architectural pattern. Parent-app gets one new reusable widget
(`ProfileHeader`) and explicit `TextTheme`/token additions to the existing `app_theme.dart`; every
screen change is a visual edit to an existing `build()` method, not a restructure. staff-console gets
one new header block per profile view, built from data each view already loads, using only existing
`base.css` tokens and the existing `StatusPill` component.

**Tech Stack:** Flutter/Dart (`parent-app`), Vue 3 (`staff-console`) — no new dependencies on either
client (no icon package added; `google_fonts` and the existing local icon usage are enough).

**Spec:** `docs/superpowers/specs/2026-09-17-ui-revamp-design-system.md`

## Global Constraints

- No new third-party packages. Parent-app icons stay Material `Icons.*` (chosen deliberately per
  subject/action, not a new icon font) inside custom tinted-chip containers — the "custom-feeling"
  effect comes from the chip treatment, not from swapping icon sets.
- Every color/radius/spacing value referenced by new or edited widgets must be a token
  (`AppColors.*`/`AppColorsDark.*` constant or a `base.css` custom property) — never an inline hex.
- Every existing widget `Key(...)` (Flutter) and `data-testid` (Vue) referenced by a test stays
  exactly as-is. Run the relevant test file after every task; a failure means the edit touched
  structure it shouldn't have.
- Dark mode is mandatory for every parent-app change: if a screen renders differently in light vs.
  dark today, the new styling must too (read from `AppColors`/`AppColorsDark`, never assume light).
- No fabricated stats. `ProfileHeader`'s stat strip only renders values the caller actually has;
  missing data omits that stat slot rather than showing a placeholder number.

## Phase 0 — Design tokens

### Task 1: Extend `app_theme.dart` with new tokens and explicit text theme

**Files:** Modify `parent-app/lib/src/theme/app_theme.dart`.

- [ ] Add to `AppColors`: `accentWarm = Color(0xFFEA7317)`, `attendanceTint`, `feesTint`,
      `timetableTint`, `messagesTint` (low-opacity tints derived from `present`/`accentWarm`/

      alpha approach against `AppColorsDark.present`/`accentWarm`/etc.).
- [ ] Add a `tabularNumberStyle(BuildContext)` helper returning
      `TextStyle(fontFeatures: [FontFeature.tabularFigures()])` merged onto the current

      pulling in `IBM Plex Mono` on mobile just for this).
- [ ] Replace the bare `GoogleFonts.plusJakartaSansTextTheme()` in both `buildAppTheme()` and
      `buildDarkAppTheme()` with an explicit override chain (same base, then `.copyWith` for
      `displaySmall` (22/700), `titleMedium` (16/700), `bodyMedium` (14/500), `labelSmall` (11/600))
      so the scale in the spec is codified, not incidental.
- [ ] Run: `cd parent-app && flutter test` — expected: all existing tests still pass (this task only
      adds constants/overrides; nothing consumes them yet).
- [ ] Commit: `git add lib/src/theme/app_theme.dart && git commit -m "feat(theme): add parent-app accent/tint tokens and explicit text scale"`.
