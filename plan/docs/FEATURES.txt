### FEAT-001 — Data model + migration plan
Domain:       infra
Complexity:   L
Dependencies: none
Description:  PostgreSQL schema (Prisma) covering users, roles, schools, campuses, academic_sessions,
              classes, sections, subjects, teachers, students, parent_profiles, student_parents,
              timetables, attendance, diary_entries(+attachments), circulars(+attachments),
              messages(+recipients+attachments), notifications, fee_structures, fee_vouchers,
              fee_items, fee_payments, receipts, files, audit_logs, device_tokens. UUID PKs,
              created_at/updated_at, FKs + indexes. Campus is a first-class column from day one
              (SchoolOS already runs two campuses).
User stories:
  - As a backend engineer, I want a normalized schema with migrations, so every later feature has a
    stable data layer to build against.
Acceptance criteria:
  - `prisma migrate dev` runs clean against a local Postgres instance.
  - Every entity from CURRENT-SYSTEM-ANALYSIS.md's "retain" list has a corresponding table.
  - A seed script creates one school, two campuses, one class/section, one teacher, one student with
    two linked parent accounts (for local dev + tests).
Edge cases:
  - A student with two parents; a parent with two children in different campuses.
Must NOT:
  - Hardcode school/campus names as enum values — campuses are data rows, not code constants.

### FEAT-002 — Auth + RBAC
Domain:       auth
Complexity:   M
Dependencies: FEAT-001
Description:  Login (email or GR-number + password), JWT access + refresh tokens with rotation,
              rate limiting/lockout, logout, forgot-password stub (OTP hook, no SMS provider wired yet).
              Roles: SUPER_ADMIN, SCHOOL_ADMIN, TEACHER, ACCOUNTS, PARENT. Server-enforced guards —
              never rely on the frontend hiding a button.
User stories:
  - As a parent, I want to log in with my email/GR-number and password, so I can see my children's info.
  - As a teacher, I want a role-scoped session, so I only see actions my role is allowed to perform.
Acceptance criteria:
  - POST /api/v1/auth/login returns access+refresh tokens on valid credentials; generic error on invalid
    (never reveal whether the email or the password was wrong).
  - 5 failed attempts within 10 minutes locks the account for 15 minutes.
  - A PARENT-role token calling an ADMIN-only endpoint gets 403, not a silently-hidden UI element.
  - Passwords hashed with Argon2 or bcrypt; refresh tokens rotate on use.
Edge cases:
  - Expired refresh token; concurrent login from two devices; role changed mid-session.
Must NOT:
  - Log passwords or full tokens anywhere, including audit_logs.

### FEAT-003 — Multi-campus + multi-child data model
Domain:       data
Complexity:   S
Dependencies: FEAT-001
Description:  student_parents join table supports one parent linked to N students across campuses;
              GET /api/v1/me/children returns only the authenticated parent's authorized children with
              campus/class/section per child.
User stories:
  - As a parent with two children, I want a single login that lists both, so I don't need two accounts.
Acceptance criteria:
  - A parent with children on both campuses gets both back from /me/children with correct campus tags.
  - A parent can never fetch a child they are not linked to (403/404, not just a filtered empty list from
    a query they could otherwise widen).
Edge cases:
  - A child transferred between campuses mid-year (historical attendance/timetable stays attributed to
    the campus active at the time).
Must NOT:
  - Require separate parent accounts per child.

### FEAT-004 — Staff console shell
Domain:       ui
Complexity:   M
Dependencies: FEAT-002
Description:  Vue 3 + TS + Vite + Pinia app skeleton. Login screen, authenticated shell with role-gated
              nav (Teacher sees Attendance/Diary/Timetable/Messages; Admin/Accounts sees Students/
              Parents/Teachers/Classes/Timetable/Circulars/Fees), logout. No feature screens yet beyond
              login + empty role-gated placeholders — those land with FEAT-006+.
User stories:
  - As a teacher, I want to log in and see only the nav items relevant to my role.
Acceptance criteria:
  - Login screen posts to /api/v1/auth/login, stores tokens, redirects to role-appropriate landing.
  - A TEACHER-role user does not see Admin-only nav items in the DOM at all (not just CSS-hidden).
  - Logout clears tokens and returns to login.
Edge cases:
  - Refresh-token expiry while the app is open (silent re-auth or clean redirect to login, not a broken
    blank screen).
Must NOT:
  - Ship a separate deployable app for Teacher vs Admin — one app, role-gated.

### FEAT-005 — Parent app shell
Domain:       mobile
Complexity:   M
Dependencies: FEAT-002, FEAT-003
Description:  Flutter app skeleton (Android first). Login screen (email/GR-number + password), secure
              token storage, multi-child switcher `[ Child Name ▼ ]` at the top of the authenticated
              shell, bottom nav (Home / Calendar / Notifications / Messages / Fees / More) as empty
              placeholder screens — feature content lands with FEAT-006+.
User stories:
  - As a parent, I want to log in on my phone and switch between my children from one account.
Acceptance criteria:
  - Login screen authenticates against the same /api/v1/auth/login as the staff console.
  - Tokens stored via secure platform storage (Keystore-backed on Android), not plain SharedPreferences.
  - Switching the child selector updates a shared app-level "active child" state that later screens will
    read (verified via a placeholder screen that displays the active child's name).
  - Session persists across app restarts until the refresh token itself expires — no forced re-login on
    every open.
Edge cases:
  - Parent with only one child (selector still present but shows no dropdown affordance, per the
    Home-dashboard spec's "Quick Actions" pattern) — treat as zero-decision UI.
Must NOT:
  - Force a fresh login every time the app is opened.

### FEAT-010 — Messages
Domain:       data,ui,mobile
Complexity:   M
Dependencies: FEAT-002, FEAT-004, FEAT-005
Description:  Two-party conversation threads. A parent may start a conversation only with their child's
              Class Teacher, School Admin, Accounts, or the Principal — never any other staff member —
              enforced server-side. `Section.classTeacherId` (new) designates the homeroom teacher used
              to resolve Class Teacher recipients (distinct from the per-subject teachers already
              assigned via Timetable). `User.isPrincipal` (new) flags which SCHOOL_ADMIN account is the
              Principal recipient. The specific staff user resolved at conversation-creation time is the
              only one who can reply to it (no shared team inbox this sprint — acceptable for this
              single-school system, same tolerance as other single-admin assumptions from Sprint 6.5).
              Staff can reply to any conversation they're a party to but cannot start a new one to a
              parent unprompted this sprint. Replaces the FEAT-001 placeholder `messages`+`recipients`
              broadcast shape with `Conversation`+`Message` tables.
User stories:
  - As a parent, I want to message my child's class teacher, the school admin, accounts, or the
    principal, so I can raise a concern directly with the right person.
  - As a parent with two children in different sections, I want to pick which child a "Class Teacher"
    message is about, so it reaches the correct teacher.
  - As a teacher/admin/accounts staff member, I want a scoped inbox of conversations addressed to me,
    so I can search, filter, and reply without leaving the app.
Acceptance criteria:
  - `POST /api/v1/conversations` (PARENT only) creates a `Conversation` + first `Message`.
    `recipientType: CLASS_TEACHER` requires `studentId` and resolves the staff recipient via that
    student's active Enrollment → `Section.classTeacherId`; `SCHOOL_ADMIN`/`ACCOUNTS`/`PRINCIPAL`
    resolve to a matching `User` (`PRINCIPAL` via `isPrincipal = true`).
  - `GET /api/v1/conversations` returns only the caller's own conversations (parent or staff side),
    with `?q=` search over participant name/body.
  - `POST /api/v1/conversations/:id/messages` is rejected (403) for anyone not already a party to that
    conversation — verified by e2e test, not just a hidden UI affordance.
  - A TEACHER/SCHOOL_ADMIN/ACCOUNTS token cannot create a new conversation to a parent (403) — parent-
    initiated only, server-enforced.
  - Every new message writes a `Notification` row for the other party and an `AuditLog` row.
Edge cases:
  - A student's section has no `classTeacherId` set yet — creation returns a clear 4xx error, not a
    500.
  - No `SCHOOL_ADMIN`/`ACCOUNTS`/principal-flagged user exists yet — creation returns a clear error.
  - A parent with children in two different sections messaging two different class teachers — each is
    a separate `Conversation` scoped to its own `studentId`.
Must NOT:
  - Let a parent message any staff member outside Class Teacher/Admin/Accounts/Principal (e.g. a
    different section's teacher) — server-enforced, not just absent from the UI's recipient picker.
  - Let staff start a new conversation to a parent unprompted this sprint.

### FEAT-011 — Notifications
Domain:       infra,ui,mobile
Complexity:   M
Dependencies: FEAT-002, FEAT-004, FEAT-005, FEAT-008, FEAT-009, FEAT-010
Description:  In-app notification center (the existing but previously-unused `Notification` table) for
              diary/circular/message events, deep-linking to the right screen in both clients. Actual
              push delivery goes behind a `PushAdapter` interface backed by a logging no-op
              implementation this sprint (same swap-later pattern as `StorageAdapter`) — real FCM
              wiring needs an actual Firebase project, which per PROJECT-STATUS is deferred to Sprint
              11-12. Attendance and fee events are excluded from this sprint's notification triggers:
              attendance is marked daily per student (a notification per mark would be noise, not asked
              for), and Fees (FEAT-012) doesn't exist as a real feature yet.
User stories:
  - As a parent, I want a bell icon showing my recent diary/circular/message alerts, so I know
    something needs attention without checking every tab.
  - As a teacher/admin/accounts staff member, I want to be notified in-app when a parent messages me,
    so I don't miss it.
  - As a developer, I want push delivery behind a swappable adapter, so wiring a real Firebase project
    later is a one-file change, not a rewrite.
Acceptance criteria:
  - `GET /api/v1/notifications` returns only the caller's own rows, newest first.
  - `POST /api/v1/notifications/:id/read` and `POST /api/v1/notifications/read-all` are scoped to the
    caller.
  - A new diary entry, a new circular (via its existing `CircularRecipient` fan-out), and a new/replied
    message each create a `Notification` row for the right recipient(s) and invoke
    `PushAdapter.send()`.
  - Staff console's existing placeholder bell in `AppShell.vue` becomes a real dropdown backed by
    `GET /notifications`, with an unread-count badge and click-to-mark-read-and-navigate.
  - Parent app gains a new bell icon in `HomeShell`'s `AppBar` (the bottom nav's "Notifications" slot
    is already Circulars, per Sprint 5-6 — left unchanged) with the same deep-link behavior.
Edge cases:
  - A notification's `entityRef` points at a conversation/diary entry/circular the user's access to
    has since changed (e.g. re-enrolled to a different section) — the deep link fails gracefully, not
    a crash.
  - `read-all` racing a new notification arriving concurrently.
Must NOT:
  - Let `PushAdapter.send()` throwing fail or roll back the triggering write — notification delivery
    is best-effort, never the cause of a 500 on the primary action.
  - Present the no-op adapter as if it were real push delivery — it must log/no-op honestly, not fake
    success.
